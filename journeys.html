Las piezas y el camino

Las specs dicen que cada pieza funciona. Un journey dice que el usuario llega a su objetivo. Atraviesa varias specs, no añade reglas y cada paso apunta a un criterio que ya existe.

Dos preguntas distintas

Una prueba de spec y un journey usan las mismas herramientas. Responden a preguntas distintas.

El journey J1 paso a paso

El operador entra, añade un cohete y programa un lanzamiento con ese cohete. Al final ve el lanzamiento en la lista. Cada parada es un paso. Arriba está la acción del usuario; abajo, la comprobación ◆.

Dónde se comprueba el resultado

Un journey tiene un solo .feature y no tiene spec.md. Su prueba tiene un test.step por paso. Cada paso termina con un expect.

specs/J1-operator-journey/J1-operator-journey.feature
# Journey: J1 · Specs: S2, S3, S1, S4
@journey @J1
Feature: [J1] El operador abre un lanzamiento

  Scenario: Programar un lanzamiento con un cohete nuevo
    # S2-R7
    Given el operador entra con su cuenta
    # S3-R1
    When añade un cohete nuevo
    # S1-R1
    And programa un lanzamiento con ese cohete
    # S4-R1
    Then ve el lanzamiento como «programado»
e2e/tests/J1-operator-journey/J1-operator-journey.test.ts
test.describe('[J1] …', { tag: ['@journey', '@J1'] }, () => {
  test.use({ storageState: { cookies: [], origins: [] } })

  test('…', { tag: '@J1-1' }, async ({ page }) => {
    await test.step('[S2-R7] Entrar', async () => {
      // formulario de login
      expect(menú).toContainText('operador')
    })
    await test.step('[S3-R1] Añadir un cohete', …)
    await test.step('[S1-R1] Programar un lanzamiento', …)
    await test.step('[S4-R1] Ver el lanzamiento', …)
  })
})

La línea marcada como expect es la comprobación del paso: solo el resultado que ve el usuario. El journey no comprueba otra vez todas las reglas de la spec. storageState vacío hace que empiece sin sesión.

Las reglas de un journey

🔗

No añade reglas E1.5

Cada paso cita un criterio que existe, como S3-R1. Si un paso no tiene criterio, el agente para e informa del hueco. No lo inventa: propone una spec nueva.

🖱️

Solo la UI E8.5

Todas las acciones y comprobaciones pasan por la interfaz. No usa la API ni las respuestas de la red.

🚪

Empieza sin sesión E8.9

Entrar es el primer paso del journey. No reutiliza la sesión guardada de las pruebas de spec.

🆕

Datos únicos E8.8

El usuario crea sus datos con nombres únicos. La semilla solo da la cuenta del actor.

◆

Un resultado por paso E8.4 · E8.7

Cada test.step termina con lo que ve el usuario. Pocos escenarios, no uno por criterio.

🧰

Las mismas skills

No hay una skill nueva. define-test tiene un modo journey para los códigos J. Usas los mismos /test-builder y /bugs-hunter.

Lo que cubre y lo que queda fuera

Cubre el journey J1Queda fuera
El operador entra, añade un cohete y programa un lanzamiento por la UIEl pasajero reserva su plaza: otro journey, que necesita una spec nueva
Los datos que crea un paso llegan al paso siguienteLas reglas de cada spec: ya las comprueban sus pruebas
El recorrido empieza sin sesiónUn navegador real cerrado y abierto otra vez
El journey se ejecuta con las specs en verde. Por eso su fallo suele estar entre dos specs, no dentro de una.

Para pensar: ¿qué demuestra el journey que no demuestran las specs?
