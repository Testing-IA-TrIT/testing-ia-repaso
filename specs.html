spec → prueba

Si cambia un requisito

  1. Busca su código en spec.md, por ejemplo R5 (US2).
  2. Abre US2-<slug>.feature y busca el escenario [R5].
  3. Abre US2-<slug>.test.ts y busca los test con @S1-R5.
prueba → spec

Si falla una prueba

  1. Lee la etiqueta del test en el informe, por ejemplo @S1-R2.
  2. Busca R2 en spec.md. El criterio dice su historia: US1.
  3. Compara el resultado de la prueba con el criterio EARS. Decide si falla la aplicación o la prueba.

Lo que no tiene código

Contexto, no pruebas

El problema, las reglas, la solución y lo que queda fuera no tienen código. No generan pruebas. Para probar una regla, escríbela también como requisito EARS.

Un nombre para cada cosa

«Spec» es la especificación funcional: spec.md. Un .test.ts prueba una historia. Por eso las pruebas no usan .spec.ts.

journeys

Journeys: cuando el objetivo cruza varias specs

Las specs prueban que cada pieza funciona. Un journey prueba que el usuario llega a su objetivo. No es una spec: no tiene spec.md ni reglas propias. Cada paso cita un criterio que ya existe.

El journey J1 paso a paso

El operador entra, añade un cohete y programa un lanzamiento con él. Al final, lo ve en la lista. Cada parada es un paso. Arriba, la acción. Abajo, la comprobación ◆.

Las reglas de un journey

  • No añade reglas E1.5 Cada paso cita un criterio que existe, como S3-R1. Si falta, el agente para y propone una spec nueva.
  • Solo la UI E8.5 Acciones y comprobaciones, siempre por la interfaz. Sin API ni respuestas de red.
  • Empieza sin sesión E8.9 Entrar es el primer paso. storageState vacío.
  • Datos únicos E8.8 El usuario crea sus datos. La semilla solo da la cuenta del actor.
  • Un resultado por paso E8.4 · E8.7 Un test.step por paso, que termina con un expect. Pocos escenarios, no uno por criterio.
  • Sus archivos Un specs/J1-<slug>/J1-<slug>.feature y un e2e/tests/J1-<slug>/J1-<slug>.test.ts, con etiquetas @journey @J1.
  • Las mismas skills define-test tiene un modo journey para los códigos J. Usas /test-builder y /bugs-hunter.

Si las specs pasan y el journey falla, el fallo suele estar entre dos specs.

Un mismo código en tres archivos para saber siempre lo que compruebas.
