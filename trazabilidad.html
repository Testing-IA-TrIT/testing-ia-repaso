Del requisito a la prueba, y vuelta

Desde un requisito, llegas a su prueba. Desde una prueba que falla, llegas al requisito que no se cumple. El camino es corto porque todos los niveles usan el mismo código.

Dos niveles, los mismos códigos

La spec dice qué debe hacer la aplicación. Las pruebas dicen cómo se comprueba. Las pruebas repiten los códigos del análisis y no crean códigos nuevos.

Un requisito, su escenario y su prueba comparten el código: R1 → [R1] → @S1-R1

El mapa de una spec

Una spec de ejemplo con dos historias y cinco requisitos. Pasa el ratón por cualquier elemento: se ilumina su camino en los tres archivos. El panel de abajo dice cómo ejecutar ese nivel.

Con el fallo, sigue la traza al revés.

Seguir la traza

Hay dos direcciones. Las dos usan solo el código y una búsqueda.

spec → prueba

Si cambia un requisito

  1. Busca su código en spec.md, por ejemplo R5 (US2).
  2. Abre US2-<slug>.feature y busca el escenario [R5].
  3. Abre US2-<slug>.test.ts y busca los test con @S1-R5.
prueba → spec

Si falla una prueba

  1. Lee la etiqueta del test en el informe, por ejemplo @S1-R2.
  2. Busca R2 en spec.md. El criterio dice su historia: US1.
  3. Compara el resultado de la prueba con el criterio EARS. Decide si falla la aplicación o la prueba.

Lo que no tiene código

Contexto, no pruebas

El problema, las reglas, la solución y lo que queda fuera de alcance no tienen código. No generan una prueba. Si una regla se debe comprobar, escríbela también como requisito EARS.

Un nombre para cada cosa

«Spec» es la especificación funcional, en spec.md. Un archivo .test.ts es el código que comprueba una historia. Por eso las pruebas no usan el sufijo .spec.ts.

Un código, tres archivos. Si una prueba no cita su requisito, no puedes saber qué comprueba.
